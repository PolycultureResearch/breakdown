# The White Cube demo

A deployable Breakdown instance over synthetic data, for client pitches.

**White Cube** is a B2C subscription app for visual artists — organize an archive
of digital images and files, track what showed in which exhibition, log what
sold. Freemium with a 7-day trial. The company does not exist; its data is
generated by [`fake_companies`](https://github.com/PolycultureResearch/fake_companies)
from a scenario config, and every anomaly in it was planted on purpose, so every
RCA conclusion the demo produces is checkable against ground truth.

- **Design and rationale:** [`../knowledge/white_cube_demo_plan.md`](../knowledge/white_cube_demo_plan.md)
- **What to actually click, in order:** [`../knowledge/demo_guided_tour.md`](../knowledge/demo_guided_tour.md)
- **The tree:** [`white_cube_tree.yml`](white_cube_tree.yml) — 18 metrics, apex `net_new_mrr`

## Running it locally

```bash
make serve          # off the committed snapshots — no dbt, no DuckDB needed
```

That is exactly what the deployed image does. To rebuild everything from the
scenario config:

```bash
make all            # generate -> dbt build -> MetricFlow -> snapshots -> verify
```

`make all` needs the `fake_companies` repo checked out beside this one (override
with `make all FAKE=/path/to/fake_companies`).

## Why the build and the runtime are split

Everything up to `make snapshots` runs the **live** dbt + MetricFlow path against
DuckDB. That is the part worth screen-sharing when a prospect asks what it takes
to point Breakdown at their warehouse — it is an ordinary dbt project and an
ordinary `mf query`.

What gets **deployed** is only the tree plus the parquet snapshots that build
produced. The running demo has no data provider at all, so it boots in seconds
and nothing can be down in the middle of a pitch.

### The two interpreters

dbt-core does not run on Python 3.14, which is what Breakdown targets — its own
bundled `mf` fails on import there. This is not a problem to solve, because
`LocalDataFetcher` shells out to whatever `mf` is on `PATH`: the semantic-layer
toolchain stays in `fake_companies`' Python 3.13 environment and the two never
have to agree on an interpreter. The Makefile puts that venv first on `PATH`.

One consequence worth knowing: this must come before any `uv run`, which
prepends Breakdown's own venv and would shadow it. That is why the Makefile
invokes `.venv/bin/breakdown` directly rather than through `uv run`.

## Regenerating when the data looks stale

The scenario runs `2024-06-01` → `2026-07-30`. When that starts to read as
historical, move `timeline.start` in
`fake_companies/configs/white_cube_b2c_app.yaml` forward, shift the anomaly
windows by the same offset, and re-run `make all`. Then update the window pairs
in `scripts/verify_white_cube_stories.py` and the guided tour together — the
verifier is what proves the stories still land.
