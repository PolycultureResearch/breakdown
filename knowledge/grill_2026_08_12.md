## Verdict

The engine is in better shape than its operational envelope, and both are in better shape than the README.

The math is right — I checked rather than assumed. `compute_shapley` matches an independently written brute-force implementation to 0.0 on a 4-parent formula with division and a squared term; efficiency holds exactly; the three-game means/covariance decomposition telescopes to the node's own gap; the `beta_raw = beta / (x_std/y_std)` denormalization algebra is correct. "Parent order is load-bearing" is honored at every engine call site. The disclosure discipline in `knowledge/roadmap.md` and the whitepaper is genuinely unusual — most of what a statistical reviewer would flag is already written down, with severity notes sharper than mine would be.

What's weak is everything between the correct math and the messy world: the provider boundary, the request lifecycle, and the documentation. Two findings are **silent wrong numbers on the flagship provider path** — the worst class this project recognizes, and the class its own roadmap is organized around. Neither is disclosed anywhere.

There are two hard blockers before either gate. Everything else is triage.

## The two that actually block

### C1 · A dbt metric's `filter` is silently dropped — the node serves the unfiltered measure
`breakdown/dbt_manifest.py:130` · **critical** · confirmed by execution · blocks both

`Metric` and `MetricInput` don't model MetricFlow's `filter` (nor `fill_nulls_with` / `join_to_timespine`), `_Node` sets `extra: "ignore"`, and `_translate_simple` never checks for one. A filtered dbt metric translates into a filterless `BindingSpec`, is **not** reported in `BridgeResult.skipped`, and the generated SQL aggregates the entire relation.

The festival's dbt project defines `food_revenue` as measure `order_total` with `filter: "{{ Dimension('order__is_food_order') }} = true"` — the single most common way a real dbt metric narrows a measure. breakdown bridges it, `doctor` passes (the grain assertion still sees one row per `order_id`), and the node labelled `food_revenue` is served *total* revenue. The whole tree is then fitted and attributed against a number several times larger than the governed metric. Nothing warns.

This is worse than a bug, because it inverts the product's core promise: the pitch is that breakdown computes over the semantic layer the client already governs. Serving a different number under the governed metric's name is the one failure that can't be argued down as a modelling caveat. `BindingSpec` has no filter field at all, so **the only correct behaviour available today is to skip the metric** — which at least surfaces in `skipped` and forces the author to notice.

The reviewer also found this is broader than metric-level `filter`: MSI models `join_to_timespine` and `fill_nulls_with` on `PydanticMetricInputMeasure` and `filter` on `PydanticMetricInput`, so a *ratio* metric whose numerator or denominator carries a filter, and any measure declaring `fill_nulls_with: 0`, are mistranslated the same way. Fix the whole set of semantics-changing input fields, not just the one.

> Fix now: skip any metric whose own filter — or whose input's filter/fill/timespine flags — are truthy, with a reason naming the construct, exactly like the existing `non_additive_dimension` skip. Real filter support (`where:` on `BindingSpec` fed by dbt's `where_sql_template`) is the follow-up, and it's ~80% of real trees, so it's a roadmap item not a patch.

### C2 · Editing a metric's `sql:`/`bind:` doesn't invalidate its snapshot — and provenance attests the new SQL for the old numbers
`breakdown/snapshots.py:39` · **critical** · reproduced · blocks the festival

`SnapshotStore._filename` keys on `(query_name, grain, kind, start, end)`. For the `warehouse` provider the query *is* the metric's own `sql:` block; for `dbt` it's the node's `bind:` block. Both are per-metric fields that fully determine the returned values. Neither is in the key.

Day 1 you ship `sql: SELECT d, amount FROM orders WHERE :start_date <= d AND d <= :end_date` → `ticket_revenue` mean 100.0, snapshot written. Day 2 you notice refunds are included, edit to `... WHERE is_refund = false ...`, restart. **The server reports 100.0 forever.** True value 60.0. And `query_provenance` is delegated straight through by `SnapshotFetcher` (`snapshots.py:163-173`), so the UI's "show query" panel displays the refund-*excluding* SQL beside the refund-*including* number — the provenance feature actively vouches for the wrong figure.

This is squarely in the path of a first deployment, because a first deployment *is* iterative tree authoring against a live snapshot dir. Nothing in `doctor`, `/health`, the manifest, or the logs says anything is stale.

> Fix: add `definition_sha` to the manifest.json record, compare on read, warn-and-refetch on mismatch. That also repairs the provenance inversion — a hit can then only be served when the statement shown is the statement that produced it.

## High severity

**H1 · One zero-denominator period NaNs the entire attribution — 500 on HTTP, silent `null`s over MCP.**
`engine/rca.py:378` · confirmed · blocks both. `shapley_attribution` evaluates a formula node per-period with no finiteness guard. One period where a ratio's denominator is 0 makes `baseline`, `gap`, every attribution, every `ci_95`, `unexplained`, `interaction` and every `ranked_causes` score NaN. On HTTP that reaches Starlette's `allow_nan=False` encoder as an unhandled **500** — after the endpoint's `ValueError` handler, so it's not the 422 path and carries no diagnostic. Over MCP it's worse: `shaping.round_floats` converts every NaN to `null`, and the agent is handed `attribution {revenue: null, order_count: null}`, `gap: null`, and a `prob_same_direction` of 0.28 — a number that is **impossible** for the max of two complementary fractions, so the one value that survives is visibly wrong on its face and nothing says so.

The trigger is not exotic. `formula: "revenue / order_count"` is the README's own documented shape (`:474`, `:557`, `:590`), and `_align_to_spine` *manufactures* the zero by design for a `kind: flow` denominator ("interior gaps are filled by kind — flow → 0", `data_fetch.py:225`). A seasonal festival produces off-season zeros naturally. The NaN also escapes `_rank_causes`' guard, because `rca.py:870`'s `min(abs(share), 1.0)` returns `nan` for `share=nan`. You already fixed this exact encoder failure one file over — `slices.py:530` carries the comment *"Starlette's `allow_nan=False` encoder as an unhandled 500"* and `:534` filters with `np.isfinite`, logged as shipped under C8 — but only for `slices.py:326`. `rca.py` never got the same treatment.

**H2 · Formula attribution is O(2ⁿ) with no cap; a wide node holds the global lock for minutes.**
`engine/model.py:145` · confirmed · blocks the festival. Measured end-to-end: 8 parents 1.5s, 10 parents 9.7s, **12 parents 50.6s** — all under `app.state.lock` (`main.py:813`), which serializes `/analyze`, `/rca/slices` and `/simulate` behind it. A festival tree with `total_revenue = tickets + food + bar + merch + camping + parking + sponsorship + …` reaches 12 parents without trying. `simulate.py:63` caps the identical enumeration at `_MAX_SOURCES = 10`; the formula path has no equivalent and no documented limit. (One correction to the finder: for an additive formula the individual coalition evaluations are *not* zero, so the affine short-circuit needs care — but the hard fan-out cap stands on its own.)

**H3 · BigQuery `DATE_TRUNC` arguments are reversed at day and month grain.**
`dbt_sql.py:62` · confirmed · blocks the festival. `_TRUNC` emits the portable `DATE_TRUNC('<part>', col)` and `_parse_dialect` deliberately parses in the *target* dialect, so nothing rewrites it — but BigQuery's signature is `DATE_TRUNC(date_expression, date_part)`. Only `("bigquery", "week")` has an override. So **every day-grain and month-grain BigQuery query breakdown generates is malformed**, the app serves degraded 503s at startup, and `doctor`'s grain assertions fail too. Week is the only usable grain. This shipped in the newest commit (`c18d150`). Secondary: even with the order fixed, BigQuery's `DATE_TRUNC` takes a DATE, so a TIMESTAMP/DATETIME event column needs `TIMESTAMP_TRUNC` — which makes the existing week override wrong too for the common dbt fact-table case. The dialect tests assert on emitted *text* only, which is exactly the blind spot that already burned you twice on Databricks.

**H4 · `MAX_CACHED_TRACES` is never enforced on the two endpoints that fit N metrics.**
`engine/rca.py:486` · confirmed · blocks the festival. `_remember_fit` — the bounded, no-downgrade writer that C8 and the "only cache, passed in explicitly" agreement rest on — is called **only** from `POST /analyze` (`main.py:743`), which fits one metric. `run_rca` and `run_scenario` (`simulate.py:414`) assign into the same dict with a bare `traces[key] = fit_metric(...)`. The reviewer drove the cache to **261 entries** through the public API. Worse, the cap constant is mis-sized independently of the wiring: a measured ADVI trace on the demo's real 830-day window is **6.66 MB**, so 256 entries ≈ **1.7 GB** against `demo/fly.toml:87`'s `memory = "2gb"`. Fixing enforcement alone still OOMs the box. The bound has to be size-aware.

**H5 · `GET /metrics/{name}` runs `az.summary` on the event loop, freezing the whole process.**
`api/main.py:693` · confirmed · blocks the festival. The one heavy engine call in the file not wrapped in `asyncio.to_thread`. Measured: 7.9s at default draws on an 830-day window, and a `/health` issued 0.3s later completed in **7.54s** — it waited. After a `draws=2000` fit (the UI's own box allows up to 5000), the same endpoint took **25.5s** and `/health` 25.2s. A 25-second total outage for every viewer, caused by one person clicking one node. The realistic worst case is worse than a single click: `runRCA` wipes `state.metricCache` (`app.js:1802`) and `clearRCA` (`:1914-1920`) then loops `GET /metrics` over every fitted metric, so one RCA-then-Clear issues N uncached summaries back to back. One-line fix; better, memoize on the `FitResult`, since the trace is immutable once fitted.

**H6 · `/rca/{name}/slices` fetches a caller-controlled unbounded window and caches it forever — even when the request then 422s.**
`api/main.py:844` · confirmed · blocks the festival. The endpoint validates only that the four dates *parse*, never that they lie inside the loaded window. `_run_slice` hands `min(ref_start, an_start) … max(ref_end, an_end)` straight to the provider. One request with `reference_start=1900-01-01` and `analysis_end=2100-12-31` fetches a 73,000-day series (293,656 rows on mock), stores **9.7 MB permanently**, and returns 422. 40 such requests left 41 permanent entries, all 422s. `slice_cache` and `flow_cache` (`main.py:286`, `:290`) have **no cap, no TTL, no eviction anywhere in the package** — C8 bounded `traces` and never looked at its two siblings. On a real provider this is worse than memory: `LocalDataFetcher.fetch_metric_sliced` shells out to `mf query --start-time 1900-01-01 --end-time 2100-12-31` with a 120s timeout, holding `app.state.lock` the whole time, so the client's own UI hangs while someone else's junk window scans their warehouse.

**H7 · The README's "real, unedited exchange" MCP transcript is unreproducible and its conclusion is inverted.**
`README.md:939` · confirmed · blocks both. Every dollar figure is 28–100× off what the bundled tree now produces. The README says revenue *fell* 1.4% from $735.7K to $725.2K/day with AOV $5,132 → $4,879. Over exactly those windows it now *rises* **2.26%**, from $26,386.5 to $26,982.1/day, AOV $184.7 → $182.2. The transcript's headline claim — "revenue was down because average order value dropped" — is false on the current tree. Its own `report_url` deep link reproduces the contradiction in one click. Root cause: C10/C11 changed the mock generator and the bundled tree; the README's copy wasn't updated in the same change. This is the MCP section, which is the strategic asset and the demo's magic moment.

**H8 · Five README "YAML reference" examples don't parse, including the one prescribed as a fix.**
`README.md:555` · confirmed · blocks both. `MetricDefinition.source` is required (`parser.py:546`), and the examples at `:438`, `:465`, `:551`, `:579`, `:620` omit it. `README:676` tells authors `sql` is an alternative to `source`; it isn't, so a warehouse-only author following that sentence also fails to parse. And the `:551` block is worse than incomplete — the pattern it prescribes **does not exist**: its comment `# derived, not fetched` is false, because `api/main.py:133` iterates `parser.config.metrics` unconditionally and a formula node is fetched from the provider like any other. The reviewer instrumented the startup path and watched the provider get asked for it. So the block the README offers as the remedy for rates over true-zero denominators is wrong twice.

## Operational, from the completeness pass

- **`BREAKDOWN_API_TOKEN` gates only `/mcp`.** `main.py:423`. Its own docstring gives the rationale — *"exposing it off loopback without a gate hands anyone who finds the URL the tree and its data"* — and then exempts every JSON data route. `curl https://host/series` returns the client's full daily history; `curl https://host/dag` serializes the whole `MetricDefinition` **including `sql` and `bind`**, so a warehouse tree publishes fully-qualified table names and WHERE-clause business logic. The operator believes the box is gated because `/mcp` returns 401. The README's API reference doesn't mention authentication at all. Cloudflare Access in front changes the exposure but not the design flaw — and it's one misconfiguration away.
- **`SnapshotStore.read` requires an exact window match** while `read_sliced` correctly trims a containing window and documents *why* that's the right call. `snapshots.py:46`. Moving `--end-date` by one day takes a snapshot-served deployment to `degraded` across every metric, for a config change that *shrank* the request. `_sliced_candidates` is already 90% of the code needed.
- **`breakdown doctor` cannot see snapshots.** `doctor.py:741`. It calls `_build_fetcher` directly, never `_wrap_snapshots`, and the word "snapshot" appears nowhere in the file — contradicting its own docstring ("proves the same code path the server will use, not a lookalike"). On the snapshot-only deployment mode the README and demo both ship, it prints `[FAIL] dbt project — no dbt_project.yml` and exits 1 against a server answering perfectly. Every failure path in the product points the user at this command.
- **The UI misdiagnoses any bootstrap error as "server unreachable".** `app.js:108`. `isTransient` is `err.status === undefined || …`, and `.status` is set only on non-ok HTTP responses — so a `ReferenceError` from the bare global `cytoscape(...)` inside `init()`'s single try block is classified as a dropped connection and routed to a retry banner that can never succeed. `index.html:7-10` loads four libraries from three CDNs with no `integrity` and no bundled fallback. On a venue or corporate network that blocks cdnjs, the client sees "Can't reach the server" and an infinite Try-again loop against a healthy server, and you both chase the wrong system.

## The weakest load-bearing assumption

**That the semantic layer's definition of a metric survives the trip into breakdown intact.**

Everything downstream is conditioned on it. The positioning thesis is that analytics engineering has already built ground truth and breakdown computes over it — that's why "clone the client's dbt repo" is the hosting plan, why the manifest bridge exists, and why `query_provenance` is a feature. The statistical machinery is only as good as the number it decomposes, and the entire correctness effort in `knowledge/` is aimed at the layer *above* that number.

C1 and C2 are the same assumption failing from opposite ends: the bridge drops a `filter` on the way in, and the snapshot layer serves a stale definition on the way out while provenance attests the new one. Neither produces an error. Both produce a confident, well-calibrated, beautifully attributed decomposition of the wrong quantity. That is the failure mode this product cannot survive at a client, because the client's only defence is to already know the answer — and if they knew, they wouldn't need the tool.

The reviewers found no defect in the Shapley math, the BSTS normalization, the grain algebra, or the DAG invariants. The load-bearing assumption isn't in any of those. It's at the seam.

## What I'd bet breaks first in the first deployment

**A ratio node with a structural zero, producing an unexplained 500 (H1).** A festival's off-season is a wall of zero denominators, `_align_to_spine` manufactures them by design for `kind: flow`, and the README's own examples steer authors straight into `revenue / order_count`. The client's analyst self-serves, hits a blank 500 with no diagnostic, and there's nothing in `/health`, `doctor`, or the logs to tell either of you why.

Second bet, and the one I'd rather you didn't lose: **C1**, quietly, with nobody noticing for weeks.

## Steelman: the alternative you didn't take

The strongest competing design is **refusing to serve any metric breakdown cannot fully account for** — no partial translation, no silent fill, no snapshot hit without a definition hash. Concretely: the bridge skips anything with an unmodelled field, `_align_to_spine` refuses rather than zero-fills a leading gap, and a snapshot miss is a hard error rather than a fall-through.

That design is *worse* for adoption. It turns "self-serve breakdown onto your semantic layer" — the thing the client's analyst did with no help, which is your strongest signal to date — into a wall of refusals on a real dbt project, where filters are ~80% of metrics. Your permissive default is why the tool demos well.

But you took the trade-off **by accident, not on purpose**, and only in one direction. `dbt_sql.py` gets it right and the reviewers praised it for exactly this: it refuses `agg: last`, joined dimensions, and entity flows rather than approximating them, and says so. `dbt_manifest.py` does the opposite for `filter` — same layer, same class of gap, opposite policy, no stated reason. Same story with the caches: `traces` is bounded with a paragraph of justification, `slice_cache` and `flow_cache` beside it are unbounded and undiscussed. And with NaN: `slices.py` filters non-finite values with a comment explaining the encoder failure, `rca.py` doesn't.

That's the pattern worth naming. It isn't that the wrong policy was chosen — it's that a policy was chosen carefully in one file and not propagated to its neighbours. **Three of the findings above are the same defect the author already fixed one file over.** A short written rule ("the provider boundary refuses rather than approximates; every cache on `app.state` is bounded; no engine result reaches an encoder unsanitized"), plus a test per rule, would have caught C1, H1, H4, H6 and M5 as a group.

## What's genuinely good

Worth saying plainly, because it's most of the codebase and the review format hides it.

The Shapley implementation is exact and verified against a brute-force oracle. The parent-order invariant holds at all six call sites. `grains.py` is careful work — `snap_window` is the identity at day grain, `resample_up` refuses rate aggregation and week→month, `_check_contiguous` raises rather than letting positional indexing drift. `slices.py` was called "one of the most carefully reasoned modules I have read this year" — the overlapping-additivity path, the Bennet fold-into-`__other__` weighting, and `_rank_by_excess`'s two-value-tie argument are all correct and all documented. `doctor.py`'s cascade-of-skips design is excellent. The "no hidden global state" agreement holds exactly.

The MCP surface is hardened better than the HTTP one: missing args, wrong types, unknown tools and path-traversal-shaped metric names all came back as structured `isError: true` payloads, nothing crashed the session, and no tool can touch a file path.

Packaging is better than most first releases: the wheel carries the static UI, both example trees, `py.typed` backing the `Typing :: Typed` classifier, and Apache-2.0 in `dist-info/licenses`.
